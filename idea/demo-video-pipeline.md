# デモ動画を作る仕組み（仕様 v1）

ステータス: 構想は確定（2026-11-03）。次は試作（今夜、別の Claude Code セッションで。指示書は `pilot-prompt.md`）

## ゴール

- **目標**：11/7 の1日で、質の高いデモ動画を仕上げられるようにする。そのために、開発の途中から毎晩、通しのプレビューを出す
- **この仕組みができた後にできること**：機能ができるたびに、録画と絵コンテの1行を足すだけで、毎晩、最初から最後までのプレビュー動画が出る。直したい所は「0:12のテロップを短く」「シーン3を2秒詰めて」のように、秒数かシーン番号で伝えれば反映される。最終日は、プレビューを手で仕上げるだけにする
- この段階では、動画の仕上がりに時間をかけすぎない

## 決まったこと

### 出力と層
1. 出すもの：**毎晩の通しプレビュー＋最終日に手で仕上げ**
2. 3つの層。上の層は、下の層を変えない
   - **素材層**：画面録画。撮り方（解像度・フレームレート・音声なし）を固定し、テロップなどを焼き込まない
   - **ベース動画**：録画をつなぎ、テロップを乗せた短い動画。雰囲気は事前に考えてから作る。一発出しにしない
   - **品質向上層**：ベース動画の上に、別の層として重ねる
3. 品質向上層に足すもの（想定の順。根拠はない）：テロップのデザイン・場面転換 → 合成音声のナレーション → ズーム・ハイライト → BGM。ただし、音声を作る順番は試作で決める
4. 雰囲気（テンポ・文字の量・色・見せ方）：過去動画の分析（`gallery-analysis.md`）の結果を見て決める

### ナレーションと言語
5. ナレーション：合成音声。**Gemini 3.8 Flash TTS**（`gemini-3.8-flash-tts`）を使う
6. 言語：日本語ナレーション＋日本語テロップ。英語テロップを後から足せるように、絵コンテに `telop_en` の列を最初から用意する

### 絵コンテ
7. 正本：リポジトリの `demo/storyboard.md`（gitの履歴で戻せる。どのAIも読める）。アーティファクトは、見て直す用に、そこから作る
8. 列：シーン／秒数／見せる画面／日本語テロップ／英語テロップ／ナレーション。修正は、秒数かシーン番号で指示する
9. 公開リポジトリなので、見せたくない内容は絵コンテに書かない

### 素材と置き場所
10. 機能ができるたびに、絵コンテに1行足して、画面録画を撮る
11. 録画・音声などの大きいファイルは、リポジトリに入れない（Drive またはローカル）

### 試作
12. 別リポジトリ（作業用の別フォルダ）・別の Claude Code セッションで、今夜、最大約2時間
13. 完了条件：絵コンテ3シーン＋録画3本から、テロップ付き30秒動画が1コマンドで出る
14. 同じ絵コンテで複数のツールを比べる。トークン数と時間を測る

## レビューで出た論点（未承認。Opus による advisor のレビュー）

1. **層の設計に矛盾がある**：音声を先に作ると、シーンの秒数（下の層）が変わり、「上の層は下を変えない」と両立しない。→ 秒数は「音声の長さ＋余白」で決める版と、絵コンテの秒数に音声を合わせる版を、試作で比べる。あわせて、**手で仕上げ始めた後は、自動の作り直しをしない**（手直しが消えるため）
2. **読みの列**：テロップとナレーションを同じ文で済ませると、英単語・数字・固有名詞を読み間違える。→ 絵コンテに「読み（ひらがな）」の列を足す
3. **審査員の言語**：審査員が英語話者なら、英語テロップは「後から」ではなく必須になる。→ 試作で日英2段を必ず試し、Discord で言語を確認する
4. **「毎回同じ映像」の基準**：ファイルの完全一致は求めず、「クリップの長さの差が ±0.2秒以内」とする。録画用には固定のダミーデータを使い、本物の Claude が動く場面は別に撮る
5. **秘密の情報が映る事故**：URL・設定画面・開発者ツールに、API キーやメールアドレスが映ることがある。→ 録画用のダミーデータを使い、書き出した後に目で確認する
6. **書き出し設定**（一般的な目安）：H.264・yuv420p・30fps固定・音声48kHz、音量はおよそ -14 LUFS
7. **日程**：YouTube は高画質版の処理に時間がかかる。機能の追加を11/6の夜で止め、11/8の早めに提出する目標が安全（機能凍結の日は、まだ決まっていない）
8. **試作の範囲**：2時間で3ツールは多い。MoviePy（または ffmpeg）と Hyperframes を必ず、Remotion は時間が余ったときだけにした
9. **試作の実行環境**：Windows の PC 上で動かさないと、Windows での動かしやすさと書き出し時間が測れない。指示書に明記した

## まだ決まっていないこと

- 動画化ツール（試作で比べて決める）
- 録画の方法（作品の形が決まってから。Web アプリなら、Playwright の自動録画が有力）
- 音声を先に作るか、ベース動画の後で足すか（試作で両方試す）
- 書き出しの頻度（案：毎晩1回、最初から最後まで通しで）
- 雰囲気（過去動画の分析の結果待ち）
- 作品の形（Web アプリで、審査員がリポジトリから簡単に試せる形を想定。未決定）
- 提出の形式・動画の長さの上限・審査員の言語（Discord の #resources / #質問 で確認する）
- BGM とフォントのライセンス
- 絵コンテを表（md）のまま読むか、YAML / JSON にするか（試作で確かめる）

## 最初の試作で確かめること

1. 同じ絵コンテと録画で、ツールごとに「1コマンドで30秒動画が出る」か
2. 秒数・シーン番号の修正が、絵コンテの編集だけで反映されるか
3. 日本語フォントの表示、日英2段のテロップ
4. 書き出し時間、導入でつまずいた点
5. ズーム・ハイライト・場面転換を、後から足せるか
6. 音声を先に作る順と、後で足す順の、直す手間の違い
7. Playwright で録画を自動化できるか（録画サイズの指定、30fpsへの変換、カーソルの描画。同じ操作を2回撮って、クリップの長さの差が ±0.2秒以内か）
8. Claude Code の使用量（試作の前後で測る）と、Gemini TTS の費用

## ツール比較の観点

1. AI操作性（1コマンドで再現できる、人の操作が要らない、エラーが分かりやすい）
2. 修正のしやすさ（秒数・シーン番号の修正が、絵コンテの編集だけで反映される）
3. 日本語（フォントの表示、日英2段）
4. 書き出し時間と、Windows PC での動かしやすさ
5. 後から足せる演出の幅
6. ライセンス（今回のハッカソンで使えるか）
7. 音声の長さに合わせて、秒数を決められるか

## ツール候補とライセンス（2026-11-03 時点）

|---|---|---|
| Remotion | 独自ライセンス（ソースは公開だが、OSIが承認するオープンソースではない）。個人と、従業員3人以下の営利組織は無料（商用も可）。4人以上は有料 | 個人参加なので無料枠。ただしOSS限定の規則があるかは要確認 |
